# Требования Studium

> Документ относится к Studium как независимому локальному приложению.
> Bender — отдельный проект; будущая интеграция использует локальный JSON-RPC
> 2.0 over stdio. Прямые импорты Bender, API/client, облачный сервер и новые
> возможности этим переносом не реализованы. Описания прежних фаз сохраняют
> технические требования; их проверки и acceptance не подтверждены этим текстом.

## Прямое дополнение Iteration 4

[Задание](iteration4-request.md) уточняет текущий UI и data-safety без Phase 7:
managed file copies независимо от источника; подтверждённое soft-delete без
Library cascade; Семинар ↔ Problem и Module ↔ Topic; lazy Bank preview; selected
attendance; categories/work/attempts/files; factual per-work Progress;
иерархия тем и навыков, period management в header, resizable tables и offline
модульная Help. Реализация и проверенные ограничения — [review](iteration4-review.md).
Append-only Attempts, UTC, UUID, FK policy и прежние формулы сохраняются.

Основание: `Studium_TZ_v0.1.docx` v0.1, §§1–7, 9, 11–19, приложения A/B; уточнения `CODEX_FIRST_PROMPT.md` и сценарий `README_START_HERE.md`. Локальный domain/data foundation выполнен в Phase 1R; базовый Windows UI и сценарий группа → студент → работа → попытки реализованы в Phase 2. Полная MVP-приёмка с файлами/Q&A/аналитикой остаётся **запланирована**; Phase 2 не объявляет выполненными критерии будущих фаз. Исходные требования сохранены, окна реализации уточнены новым roadmap; Phase 0 не реализовала функционал. ID ниже нужны для связи задач, проверок и приёмки, а фазы обозначают основное окно реализации.

## Стратегия проверки в следующих фазах

По §19: unit-тесты статусов и показателей; repository/DB-тесты ограничений, миграций и soft delete; UI-тесты матрицы и форм; сквозной сценарий группы/работы/переделок/фото/вопроса; позднее API, идемпотентный импорт, outbox, конфликт двух устройств и восстановление загрузки. Точные неоднозначные формулы фиксируются до написания соответствующей реализации.

Приёмка Phase 0 определена отдельно в [roadmap.md](roadmap.md); выполненные проверки — в [done.md](done.md).

## Проверенная коммуникационная часть Phase 5

FR-12–FR-14 реализованы в объёме отдельного задания: известный Student, ordered original Message, учебный контекст и FileAsset; manual paste/каналы/UTC и derived states. Thread/unknown participants, автоматические внешние adapters и AI verification не объявляются выполненными. AC-08/09/11/12 покрыты synthetic application/Qt/native сценариями; весь широкий MVP с analytics/единой лентой/StudentNote не объявляется завершённым. Отчёт — [done](done.md), контракты — ADR-027–ADR-029.

## Уточнённый analytics contract Phase 6

Отдельное задание 2 октября 2026 уточняет FR-09/FR-16 и AC-10: AttemptItemResult с outcome/score, current progress/attempts/timeliness/attendance, Topic/Skill evidence, Questions/response time и Group/Assessment/time-cutoff DTO. Error tags, mastery/«проблемные темы», педагогические оценки, prediction/AI, ratings и полный export subsystem не входят в это задание. Требования исходного широкого ТЗ остаются будущими, без выдачи интерпретаций за факты.

Минимальная аналитика использует [явные формулы](analytics.md), отличает 0 от None, distinct UUID предотвращают double counting parent/child и many-to-many context. Semantic lock защищает исторический смысл содержания после первой Attempt; существующие до v5 изменения без audit нельзя восстановить. Срок — точный due_at, календарный Lesson остаётся LocalDate. TopicSkill не подменяет LessonSkill; OPEN-004/009 и общий audit/override scope остаются открыты в остаточной части. Реальные результаты tests/migrations/performance/native checks фиксируются в [done.md](done.md), а пользовательская приёмка остаётся отдельным шагом.
