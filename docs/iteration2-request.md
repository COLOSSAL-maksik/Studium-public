============================================================
1. ОСНОВНАЯ ИНФОРМАЦИОННАЯ МОДЕЛЬ STUDIUM
============================================================

Нужно привести приложение к следующей логике.

Главная иерархия:

DISCIPLINE
    ↓
WORK PROGRAM / РАБОЧАЯ ПРОГРАММА
    ↓
GROUP + DISCIPLINE + WORK PROGRAM
    ↓
ежедневная учебная деятельность

Пример:

Дисциплина:
«Сопротивление материалов»

У неё могут быть несколько рабочих программ:
- Сопромат / направление МТ / осень 2026
- Сопромат / другое направление / осень 2026
- другая версия программы и т.д.

Разные группы могут изучать одну дисциплину,
но работать по разным рабочим программам.

Группа может иметь несколько дисциплин,
каждая из которых должна быть связана с конкретной WorkProgram.

Не хранить группу просто как «группа + дисциплина».
Рабочая программа должна быть явной частью контекста.

------------------------------------------------------------
1.1 Discipline
------------------------------------------------------------

Discipline — общий контейнер предмета.

Например:
«Сопротивление материалов»

На уровне дисциплины живут:
- общий каталог Topics;
- общий каталог Skills;
- reusable Problem Bank;
- reusable методические материалы;
- литература;
- база знаний / типичных ошибок и вопросов;
- определения ДЗ/РК, которые могут использоваться несколькими WorkProgram.

Topics и Skills должны быть сквозными внутри дисциплины.

Один Skill нельзя создавать заново для каждого ДЗ/РК.
Один и тот же Skill может использоваться:
- в Topic;
- в Homework;
- в ProblemBankItem;
- в Control Work;
- в конкретной задаче РК;
- при проверке РК;
- в student analytics;
- в group analytics.

------------------------------------------------------------
1.2 WorkProgram
------------------------------------------------------------

Ввести/довести до полноценного состояния сущность рабочей программы дисциплины.

Рабочая программа относится:
- к Discipline;
- к направлению / образовательной программе;
- к конкретной версии/учебному периоду.

Нужно хранить как минимум:
- название;
- Discipline;
- направление;
- факультет при необходимости;
- версия / учебный год;
- Semester type: Осенний / Весенний;
- дата начала первой учебной недели;
- количество учебных недель;
- официальный PDF рабочей программы;
- Modules;
- набор Topics;
- набор Skills;
- набор Homework;
- набор Control Works;
- seminar/lecture materials;
- Literature links.

Типичный семестр, например:
17 недель.

НЕ генерировать автоматически 50+ учебных недель на весь год.

AcademicWeek:
- начинается с 1;
- нечётная = числитель;
- чётная = знаменатель;
- отображение:
  «5 неделя — числитель»
  «6 неделя — знаменатель».

Все week selectors должны быть ограничены длительностью WorkProgram/Semester.

------------------------------------------------------------
1.3 Modules
------------------------------------------------------------

Каждый семестр делится на модули.

Добавить сущность/структуру ProgramModule.

Например:

Модуль 1
недели 1–6

Модуль 2
недели 7–12

Модуль 3
недели 13–17

Модуль должен иметь:
- название;
- порядок;
- start_week;
- end_week;
- WorkProgram.

ДЗ, РК, занятия и аналитика могут относиться к модулю.

Суммарная структура модулей не должна выходить за duration семестра.

============================================================
2. ДЗ И РК: ОПРЕДЕЛЕНИЕ И ПРИМЕНИМОСТЬ К ПРОГРАММАМ
============================================================

Очень важно разделить:

1. определение работы;
2. применение работы в конкретной WorkProgram.

ДЗ и РК принадлежат Discipline.

Но каждая работа имеет many-to-many applicability:
к каким WorkProgram этой дисциплины она относится.

Например:

ДЗ1:
Сопромат
применяется только в WorkProgram МТ.

РК1:
Сопромат
применяется одновременно в:
- WorkProgram МТ;
- WorkProgram Э;
- WorkProgram другой специальности.

Нельзя связать работу с WorkProgram другой Discipline.

Связь Work ↔ WorkProgram должна хранить program-specific параметры:
- Module;
- порядок;
- planned issue week;
- planned due/conduct week;
- при необходимости конкретную дату;
- другие program-specific scheduling data.

То есть не дублировать одинаковый РК для каждой программы.

При работе внутри группы:
Studium по умолчанию показывает только ДЗ/РК,
применимые к WorkProgram этой группы.

Оставить возможность создать «Внеплановую работу»,
но это исключение, не основной workflow.

16. РК — ПРОВЕРКА ПО ЗАДАЧАМ И SKILLS
============================================================

РК может содержать:
2, 3, 4 и т.д. задачи.

Нельзя считать РК только одним общим статусом.

При проверке преподаватель должен фиксировать результат
ПО КАЖДОЙ ЗАДАЧЕ.

Например:

Задача 1  ✓ зачтена
Задача 2  ✗ ошибка
Задача 3  ✓ зачтена

Кроме этого внутри каждой задачи нужно отметить,
какие Skills студент продемонстрировал:

Skill A → Correct
Skill B → Incorrect
Skill C → Partial / если текущая модель это поддерживает

Не создавать новый Skill прямо для этого результата.
Выбирать из сквозных Discipline Skills.

Если Problem уже связан со Skills,
показывать их автоматически
и позволять отметить результат.

При необходимости разрешить добавить другой Skill из Discipline.

Использовать существующий AttemptItemResult / ItemOutcome,
если он подходит.
Не плодить параллельную analytics модель.

Это factual evidence.
Не делать вывод:
«студент освоил навык».

Analytics может показывать:
сколько раз Skill был продемонстрирован правильно/ошибочно,
но не mastery score.
