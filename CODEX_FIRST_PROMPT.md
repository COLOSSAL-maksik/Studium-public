# Studium — первый промпт для Codex

> Документ относится к Studium как независимому локальному приложению.
> Bender — отдельный проект; будущая интеграция использует локальный JSON-RPC
> 2.0 over stdio. Прямые импорты Bender, API/client, облачный сервер и новые
> возможности этим переносом не реализованы. Описания прежних фаз сохраняют
> технические требования; их проверки и acceptance не подтверждены этим текстом.

Мы начинаем разработку нового приложения **Studium** — персональной системы преподавателя для Windows и Android, предназначенной для учёта студентов, учебного процесса, работ, попыток сдачи, вопросов/ответов, файлов и будущей аналитики прогресса.

В корне репозитория находятся исходные проектные материалы и ТЗ. Сначала внимательно изучи все существующие документы. **Не начинай реализацию функционала приложения до завершения Phase 0.**

## Цель Phase 0

Подготовить репозиторий Studium к последовательной, контролируемой разработке.

## Задачи

1. Проанализируй существующее ТЗ, архитектурные схемы и README.
2. Исходные проектные материалы считай source-of-truth для Phase 0. Не удаляй и не переписывай их без необходимости.
3. Создай в корне `AGENTS.md` с правилами работы coding agent.
4. Создай структурированную документацию проекта:

```text
docs/
  concept.md
  requirements.md
  architecture.md
  data-model.md
  ui-navigation.md
  roadmap.md
  todo.md
  done.md
  decisions.md
```

5. Подготовь целевую структуру репозитория, ориентируясь на:

```text
studium/
├── AGENTS.md
├── README.md
├── docs/
├── apps/
│   └── studium_app/        # Flutter: Windows + Android
├── services/
│   └── api/                # future FastAPI backend
├── packages/
│   ├── domain/
│   ├── database/
│   └── sync/
├── infra/

└── tests/
```

На Phase 0 не создавай production-код Flutter/FastAPI и не устанавливай зависимости только ради заполнения структуры.

## Архитектурные принципы Studium

- клиент: Flutter;
- целевые платформы: Windows и Android;
- offline-first;
- локальное хранилище: SQLite;
- в перспективе сервер: FastAPI + PostgreSQL;
- синхронизация между устройствами должна быть отдельным слоем;
- фотографии, сканы, PDF и другие документы хранятся через модель `Attachment`, а не в виде произвольных полей сущностей;
- история попыток сдачи неизменяема по смыслу: новая переделка создаёт новую `Attempt`, а не перезаписывает предыдущую;
- исходные факты учебного процесса должны быть отделены от аналитических/AI-выводов;
- архитектура должна позволять позднее подключить OCR, Vision и AI-анализ без переработки доменного ядра;
- локальный MVP должен оставаться полезным даже без backend и AI.

## Минимальный домен

Используй наименования сущностей из ТЗ. Основные сущности должны включать как минимум:

- `AcademicTerm` — учебный период/семестр;
- `Course`;
- `StudentGroup`;
- `CourseOffering` — связь дисциплины, группы и периода;
- `Student`;
- `Enrollment` — история привязки студента к потоку;
- `Topic`;
- `Skill`;
- `Lesson`;
- `LessonTopic`;
- `Attendance`;
- `Assessment`;
- `AssessmentItem`;
- `AssessmentTopicSkill`;
- `StudentWork`;
- `Attempt`;
- `AttemptItemResult`;
- `Grade`;
- `Attachment`;
- `StudentNote`;
- `CommunicationThread`;
- `ThreadParticipant`;
- `CommunicationMessage`;
- `QuestionCase`;
- связи вопроса с `Topic`, `Skill` и `Assessment`.

Не вводи параллельные сущности вроде `Assignment`/`TeachingGroup`, если они дублируют `Assessment`/`CourseOffering` из ТЗ. Не упрощай `Attempt` до единственного текущего статуса работы: Studium должен сохранять историю предъявлений и переделок.

## Communication / Q&A

Вопросы студентов из Telegram, email и других каналов являются частью учебной истории, а не обычными заметками.

`QuestionCase` / сообщения должны иметь возможность связываться с:

- `Student`;
- `CourseOffering`;
- `Assessment`;
- `Attempt`;
- `Topic`;
- `Skill`.

Сырые факты общения — исходный текст вопроса, ответ преподавателя, дата, канал и вложения — должны храниться отдельно от смысловых/AI-выводов.

## Roadmap

Зафиксируй следующие фазы:

- **Phase 0** — repository/bootstrap/documentation
- **Phase 1** — domain model + local SQLite
- **Phase 2** — Windows MVP: groups/students/assignments/attempts
- **Phase 3** — lessons/topics/skills
- **Phase 4** — attachments/photos/scans
- **Phase 5** — student questions and teacher answers
- **Phase 6** — Android UX
- **Phase 7** — FastAPI/PostgreSQL server
- **Phase 8** — offline synchronization
- **Phase 9** — analytics
- **Phase 10** — OCR/Vision/AI

Не переходи к следующей Phase без отдельного задания. Названия сущностей и терминов должны оставаться согласованными с ТЗ.

## Правила для AGENTS.md

Обязательно зафиксируй:

1. Перед изменениями читать релевантные документы из `docs/`.
2. Не менять архитектуру молча; существенные решения фиксировать в `docs/decisions.md`.
3. Не удалять существующие файлы ради их полного пересоздания, если достаточно локального изменения.
4. Делать небольшие, проверяемые изменения.
5. Не переходить к следующей Phase без явного задания пользователя.
6. После законченной задачи обновлять `docs/done.md` и `docs/todo.md`.
7. Запускать доступные проверки/тесты после изменений.
8. О блокерах сообщать явно, а не обходить их скрытно.
9. Не добавлять зависимости без объяснения причины.
10. Не добавлять преждевременно сервер, cloud sync или AI, если текущая Phase этого не требует.
11. Не хранить производные AI-оценки как исходные факты.
12. Сохранять обратную совместимость данных внутри одной фазы, когда это разумно.
13. Новые сущности и миграции должны сопровождаться тестами на ключевые инварианты.

## Неоднозначности

Если в исходных документах есть противоречие или неоднозначность:

- не угадывай молча;
- выбери наиболее консервативный вариант, достаточный для Phase 0;
- запиши вопрос или предположение в `docs/decisions.md` со статусом `OPEN`;
- не раздувай Phase 0 ради решения вопроса, который относится к более поздней фазе.

## Git

Если каталог ещё не является Git-репозиторием:

- инициализируй Git;
- создай подходящий `.gitignore` с учётом будущих Flutter/Dart, Python, IDE, local DB, build artifacts, secrets и локальных файлов-вложений;
- не коммить секреты, локальные БД, пользовательские сканы и generated build artifacts.

## Результат Phase 0

В конце работы:

1. Покажи итоговое дерево созданных/изменённых файлов.
2. Кратко перечисли принятые архитектурные решения.
3. Перечисли все `OPEN`-вопросы.
4. Перечисли выполненные проверки.
5. Убедись, что `docs/todo.md` начинается с задач Phase 1, но **не выполняй их**.
6. **Не создавай Flutter-приложение, backend и доменную реализацию в рамках этой задачи.**

Главное правило Phase 0: **качество и устойчивость основы важнее количества созданного кода.**
